# v0.25.0：远程访问时把工作区文件「下载到本机」

作者：ddj，2026-11-03。

## 背景与动机

经 `@linxin666/dsh-remote-web-ui` 之类的远程访问插件打开 DSH 后，
本插件的资源管理器已经能正常浏览远端工作区（v0.24.0 修好了通道），
但**文件内容拿不回本地**：想看一个文件，只能到远端机器上另找途径下载、再传回浏览器所在机器，
远程调试时这一步反复出现，成本高且别扭。

「下载」本身不该由用户在两个环境之间手工搬运，它应该是资源管理器的一个动作。

## 实现方式

新增右键菜单项 **下载到本机**，仅在远程访问页出现：

- 文件右键 → 直接下载该文件（原文件名、原字节，不打包）。
- 文件夹右键、根空白区右键 → 弹出确认框，按需懒加载展开目录树、逐级勾选文件后**逐个**下载。

几个关键取舍：

- **可见性判据复用既有远程通道**：`src/shared/remoteChannel.ts` 新增 `isRemoteChannel()`
  （即 `channelPrefix() !== ''`），与 v0.24.0 的通道前缀同源。本机回环页面不出现该条目，
  且 `visible` 为假时菜单根本不会执行 `run`，不会产生任何请求。
- **取字节不新增 host 路由**：直接复用既有读取链——先走 `edrv.readBinary`
  的二进制直出（`application/octet-stream` + `x-edrv-*` 头）；远程代理只放行
  `content-type`/`content-length` 等白名单头，自定义头会被丢弃，此时
  `readBinaryPreview` 会自动回落 `edrv.read` 的 base64 分支。功能在两种通道下都可用，
  只是远程下体积偏大约三分之一。
- **逐个下载而非打包**：确认框勾选多少个文件就下发多少次单文件下载。不引入 zip 依赖，
  也不改变「下载的是原文件」这一语义；单个文件失败只记录在结果里，不中断同批其余文件。
- **32MB 硬上限显式呈现**：与图片预览共用宿主 `BINARY_READ_CAP`，超过的文件在弹窗内
  标注「超过 32MB」并禁用勾选，而不是让用户点了才发现失败。
- **确认框复用 `ModalShell`**：自动满足浮层契约（`data-edrv-view` 根节点、z-index 阶梯、
  Esc / 遮罩关闭），样式全部以 `[data-edrv-view]` 前缀隔离，不污染宿主样式。

未采用的方案：

- **生成 zip 后单次下载**：需要把整棵子树先读进内存再压缩，目录稍大就会顶到读取上限；
  且用户明确要求「不打包」，希望拿到的是原文件。
- **新增 `edrv.download` 直链路由（`Content-Disposition: attachment`）**：需要新挂 GET 路由、
  额外过一遍鉴权与越界校验，并且远程代理下的响应头白名单行为还要重新验证；
  复用既有 RPC 读取链已经能拿到同样字节，不值得为此扩大 host 侧攻击面。
- **目录一键整树下载**：同样是「隐式拉全树」的问题，且无法在下载前让用户看到体积与内容；
  改为展开后可勾选 + 「全选已展开」，把选择权交回用户。

## 验证

- `npm run typecheck` → 0 error。
- `npm run test` → 全量 287 文件、3715 通过 + 22 跳过；`node --test tests/nativeOpen.test.mjs` 9/9。
- `npm run build` → host 与 client 四 bundle 均产出。
- 本机 GUI 冒烟（注入 `window.__DSH_REMOTE_CHANNEL_BOOT__ = {}` 模拟远程座位）：
  菜单出现且位于「复制相对路径」与「重命名…」之间、非远程状态不出现；
  单文件下载触发正确文件名与 `application/octet-stream` 响应；
  根/文件夹弹窗展开 105 行、单选 1 / 全选已展开 82 / 清空 0、取消可关闭；
  勾选 2 个文件逐个下载成功，干净刷新后控制台无新增报错。

**未验证项**：真实远程设备（真远程插件 + 真配对链路）下的端到端下载未验收。
本机没有 `/remote` 路由，冒烟时用 fetch 重写前缀做等价验证；通道前缀本身由 v0.24.0 覆盖。
